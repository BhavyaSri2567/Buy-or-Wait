# Buy or Wait? — Solution

## Run it

```bash
cd hackerrank-orchestrate-september26
pip install pandas requests
python3 code/main.py
```

Writes predictions to `output.csv` (repo root) and a token/cost report to
`code/evaluation/usage_report.md`.

Optional: set `ANTHROPIC_API_KEY` to enable image reading (for financial
events with a blank `amount`) and LLM fallback interpretation of any message
that doesn't match a known template. Without a key the pipeline still runs
end-to-end using deterministic fallbacks (see "Known limitations").

Self-check against the 25 solved examples in `dataset/sample_requests.csv`:

```bash
python3 code/evaluation/main.py
```

## Architecture

```
code/
  main.py              entry point: load -> per-user model -> decide -> write CSV
  engine/
    io_utils.py         CSV loading with typed dates
    fx.py                multi-hop currency conversion over monthly rate snapshots
    extraction.py        regex classifier for the ~30 templated message families (EN/ID)
    llm.py               optional Anthropic API client (images + fallback message parsing)
    events.py            per-user cash-flow reconstruction: dedupe, status filtering,
                          blank-amount resolution, recurring-series detection,
                          message-driven amendments
    forecast.py           90-day daily balance simulation, amount_safe_to_pay,
                           earliest_date_for_full_payment, plan safety checks
    plans.py               candidate plan generation (full/partial/installments/wait),
                            spending-change search, 6-rule ranking
    decision.py             orchestrates the above into one output row
  evaluation/
    main.py               scores predictions against sample_requests.csv
    usage_report.md        generated by main.py on each run
```

## Approach

1. **Deterministic core, LLM as an assist, not a dependency.** All arithmetic
   (currency conversion, balance forecasting, plan ranking, format rules) is
   plain Python so it's reproducible and auditable. The LLM is only invoked
   for two narrow, genuinely unstructured tasks: reading an amount off a
   scanned image, and (rarely) classifying a message that doesn't match a
   known template.
2. **Messages are heavily templated** (bilingual EN/Indonesian, ~30 distinct
   template families for salary changes, rent increases, pending payouts,
   refunds, investment settlements, scams, etc.). `extraction.py` matches
   these with precise regexes rather than a general LLM call, which is
   cheaper, faster, deterministic, and auditable.
3. **Untrusted content.** Message/image content is only ever mapped into a
   fixed, closed set of signal types. A scam message asking the user to "pay
   a release charge" is classified `scam_ignore` and never creates a
   payment or income event — embedded instructions never reach the decision
   logic.
4. **90-day safety check.** For each request we build a per-day net-cash-flow
   array from `request_date` to `request_date + 90d` (actual scheduled/
   settled events + detected recurring series + message amendments), turn it
   into a running balance, and compute a suffix-min of "slack" (balance −
   minimum_balance). `amount_safe_to_pay` is the slack today capped at
   `requested_amount`; `earliest_date_for_full_payment` is the first day the
   suffix-min from that day forward covers the full amount.
5. **Plan ranking** follows the six tie-break rules in `problem_statement.md`
   exactly (deadline compliance, no spending changes, minimize total paid,
   earlier start, fewer payments, lowest `payment_option_id`).

## Known limitations / next steps

Built as a first working pass; the self-eval script currently scores ~52%
status accuracy / ~56% method accuracy on the 25 solved samples. The highest-
leverage improvements for someone continuing this within the 24h window:

- **Recurrence detection** is a simple coefficient-of-variation heuristic on
  historical settled events. It sometimes over- or under-projects expenses
  (e.g. mixing multiple sub-patterns in one category, or being too strict on
  interval consistency). Tightening this against `sample_requests.csv` is
  the single biggest lever.
- **Message amendments** are applied to the *whole* projected series (e.g.
  "salary increased" changes every future occurrence); some templates
  ("temporary" pay changes) are only meant to apply to the next occurrence —
  partially handled but not exhaustively tested against every template.
- **Failed-transaction retries** (`failed_retry_note`) are currently dropped
  rather than re-scheduled, since the message doesn't give a new date.
- **Spending-change search** is a single greedy pass (by largest gain first,
  up to 3 changes); it doesn't explore alternative subsets that might satisfy
  the "no spending changes preferred" tie-break more cleanly in edge cases.
- Enabling `ANTHROPIC_API_KEY` will improve coverage on the 16 blank-amount
  events (currently a conservative category-median / exclude fallback) and
  any message text that falls outside the known templates.
